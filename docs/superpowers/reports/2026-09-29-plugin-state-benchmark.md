# O7：Memory JSONL 与 Router 状态文件性能基线

测量日期：2026-10-03。规格：[follow-up optimization O7](../specs/2026-09-29-openclaw-followup-optimization.md)。本报告只描述本机合成负载；没有用户工作负载 SLO，也没有存储迁移或生产环境结果。

## 方法与可复现输入

- 命令：`node scripts/benchmarks/plugin-state.mjs --seed 20260929 --memory-counts 1000,10000,100000 --router-counts 100,1000,10000 --runs 5`。完整运行两次，六组对应的 SHA-256 数据 hash 全部相同；每个可测组各 1 次预热和 5 次正式采样，失败样本单独计数。
- 被测实现直接从当前 TypeScript 源码加载：`MemoryStore`（`extensions/memory/src/store.ts`，SHA-256 `6cd9c3091fa20c73eedd1b2faa1e99bd0e245c27ee591c11baba79270cce5d24`）与 `DurableRouteStore`（`extensions/router/src/durable-store.ts`，SHA-256 `bacb81ca19bb88069cc7a34adda8799d076141c968d00f3c62fce62e7c434e00`）。`tsx 4.22.3` 是明确的根开发依赖，用于加载这些源码。
- 机器：Apple M4 Pro / 12 CPU / 24 GiB RAM；Darwin 27.0.0；Node v24.18.0。临时目录在系统 `tmpdir()` 下，每组独立创建并在 `finally` 清理。运行时约 14 GiB 空闲，脚本要求保留 8 GiB，并限制单组估计输入为 512 MiB。
- 数据是由固定 seed 生成的匿名合成记录，固定 `benchmark-agent` / `benchmark-session`、关键词 `needle`，不含真实用户内容。Memory 使用 L1 会话隔离、明文 JSONL、默认 `maxSearchBytes=16 MiB`、默认 `maxRecordBytes=64 KiB`；Router 使用明文 JSON 状态、审计开启、默认 `maxPendingTasks=10000`、默认 `maxPayloadBytes=1 MiB`。加密和跨会话检索没有在这组基线中启用，不得将结果外推到这些配置。
- Memory 先用真实 `appendRecords` 写满独立存储，再预热并调用真实 `createSearchManager(...).search("needle", {sessionKey})`。每次搜索需有命中；扫描字节取完整 JSONL 文件的实际大小，因可测组均低于 `maxSearchBytes` 且搜索实现扫描完整文件，此值等于本负载实际顺序读取量。记录/秒吞吐按记录数 ÷ 查询总耗时计算。
- Router 用**一次**真实 `enqueueBatch` 预置指定数量的待投递任务，准备耗时不算入采样；随后预热和 5 次真实 `markFailed(..., nextAttemptAt)`，每次都执行状态复制、完整状态文件写入、fsync 与 rename。每次调用均传入同一个原始任务对象（`attempts=0`），因此这是固定规模状态更新基线，**不是同一任务连续第 2–6 次真实重试**。写入字节按每次完成后实际 `delivery-state.json` 大小累加，仅统计主状态文件的逻辑写入字节，不代表文件系统物理写放大或 lease 元数据写入。吞吐单位是状态更新/秒。
- P50/P95 用 5 次成功采样的线性插值百分位；失败样本绝不写为 0 ms，统计中的 `sampleCount` 保留失败数。事件循环延迟为 `monitorEventLoopDelay({resolution:1})` 在操作期间的最大值，对有有效 tick 的样本取 P95，单位 ms；不足 1 ms 的短操作可能无 tick，此时保留 `null`，不填 0。准备、预热、采样各自记录。

## 瓶颈和决策

1. Memory 10k 的文件约为 1k 的 10 倍，检索 P50 约增至 8–9 倍，符合顺序 JSONL 扫描的成本特征。100k 合成数据预估 24.05 MB，超过默认 16 MiB 搜索预算；维持相同检索完整性时本组被拒绝。不能将更高规模的“只扫前 16 MiB”包装成完整检索结果。
2. Router 本组的每次 `markFailed` 状态更新都会重写完整 JSON 状态文件并执行同步持久化。100→10k 时，每 5 次主状态文件逻辑写入由约 0.14 MB 增至约 13.68 MB，P50 从约 8–10 ms 增至约 27–30 ms；高频更新会放大写入与事件循环影响。本机两轮不足以给出生产吞吐上限，也未测连续多次真实重试的变化。
3. **当前建议：保留现有实现及容量门禁。** 对 Memory 100k 完整检索、高频 Router 更新有明确需求时，先收集真实工作负载、查询命中/隔离/加密约束及 SLO，再单独制定 SQLite/索引或 worker 方案的增量规格与迁移/回滚验证。本任务未更改生产存储，也未迁移用户数据。

可复核命令：`node --test scripts/benchmarks/plugin-state.test.mjs`；上述完整 CLI 连续两次。两轮原始 CLI 输出保存为[第 1 轮 JSON](2026-10-03-plugin-state-run-1.json)和[第 2 轮 JSON](2026-10-03-plugin-state-run-2.json)，包括未舍入的每次 `durationMs`、`eventLoopDelayMs`（缺测为 `null`）、配置、源码 hash、硬件、预热和容量拒绝状态。附件仅将系统临时目录路径替换为 `<system-tmpdir>`，其余数值与原始输出一致。
